# ユースケース層の CQS

この文書は、ユースケース層のハンドラーを、コマンドとクエリに分けるルールを並べる。コマンドは状態を変え、ドメインのデータを返さない。クエリは状態を変えず、データを返す。分けておくと、ハンドラーの名前と置き場所だけで副作用の有無が分かり、レビューで確認する観点もハンドラーの種類ごとに決まる。

構造の段階([構造の段階の選び方](./scale-selection.md))によらず、同じルールを適用する。domain 層と infrastructure 層は作らない。小規模では command と query から ORM を直接使う。中規模以上では、ORM を feature の中の `repository.ts` に限り、`src/features/<feature>/` を `src/api/features/<feature>/` と読み替え、[中規模以上の差分](#中規模以上の差分) も読む。

UI のイベントハンドラーと純粋関数は、この文書の対象ではない。

## Command と Query

### Command

**必須**

- 一つのファイルに一つの command を置く(`commands/place-order.command.ts`)。入力型、ハンドラー関数、結果型を同じファイルに書く。
- 入力は一つのオブジェクトで受け取り、Zod のスキーマで検証する。
- 戻り値は、作成・更新した対象の ID(必要なら楽観ロック用のバージョン)か、想定内の失敗を表す判別可能なユニオンにする。ドメインのデータ(エンティティや一覧)は返さない。画面が更新後の値を必要とするときは、command の後に query を呼ぶ。

```ts
type PlaceOrderResult =
  | { ok: true; orderId: OrderId }
  | { ok: false; reason: "out_of_stock" | "credit_limit_exceeded" };
```

- 在庫切れのような業務上の失敗は結果型で返し、DB の接続断のような想定外の失敗は例外にする。
  - 理由: 想定内の失敗を型に含めると、呼び出し側が処理し忘れたときに型チェックで検出できる。
- 一つの command が一つのトランザクションを持つ。書き込むテーブルは、自分の feature が所有するものに限る([Go のサービスへ切り出せる状態を保つ](./tech-selection.md#go-のサービスへ切り出せる状態を保つ))。中規模以上では読み取りも自分の feature のテーブルに限る([構造](./principles.md#テーブルの所有))。

### Query

**必須**

- 一つのファイルに一つの query を置く(`queries/get-order.query.ts`)。
- 戻り値は画面や呼び出し側が使う形の型にする。ORM のエンティティをそのまま返さない。
- 該当がないときは、単一の取得なら `null`、一覧なら空配列を返す。

### Service と feature 間の呼び出し

service の切り出し方と、feature 間で呼べるもの(service と query だけ。command は `app/` からだけ呼ぶ)は、[構造](./principles.md#service-の切り出し) と [公開 API](./principles.md#公開-api) に従う。

## 中規模以上の差分

[Command と Query](#command-と-query) のルール(ファイルの単位、入力の検証、戻り値、結果型、トランザクション)はそのまま適用する。違いは次のとおり。

### ドメインモデル、リポジトリ、入力のスキーマ

**必須**

- 判断に使う業務ルール(不変条件、状態遷移、計算)は `src/api/features/<feature>/entity.ts` の純粋関数に置き、command から import する([構造](./principles.md#ドメインモデルentityts))。
- command と query は ORM を直接使わず、同じ feature の `repository.ts` の関数で読み書きする([構造](./principles.md#リポジトリrepositoryts))。
- 画面の入力検証にも使う入力の Zod のスキーマは `src/shared/features/<feature>/` に置き、command と画面で同じものを使う。サーバーだけで使うスキーマは command のファイルに書く。
- command は、`repository.ts` で読む → `entity.ts` の関数で判断 → `repository.ts` で書く、の順に書く。判断の途中で I/O をしない。
  - 理由: 判断の部分を DB なしでテストでき、command のテストは書き込まれた内容と結果型の確認に絞れる。
- neverthrow を採用したサービスでは、結果型を `Result` / `ResultAsync` で表す([エラー処理の方針](./tech-selection.md#エラー処理の方針))。

### テスト

**必須**

- `entity.ts` と `src/shared/features/<feature>/` の関数は、モックなしで入力と出力を検証する。
- `repository.ts` は、テスト用のデータベースに対して検証する。
- command と query は、テスト用のデータベースに対して検証する。command では書き込まれた内容と結果型を、query では返す値を確認する。

### リードモデルと CQRS

既定は、書き込みと読み込みが同じデータベースを使う軽量な構成である。query は、画面に合わせた SQL やビューを使ってよい。ただし、他の feature のテーブルを JOIN しない([構造](./principles.md#テーブルの所有))。

**必須**

- query 専用のテーブルやビュー(リードモデル)を作るときは、query だけが読む。command の判断に使わない。
- マテリアライズドビューは、更新(`REFRESH`)までの古さを許容できる画面にだけ使う。更新直後の値が要る画面には、通常のビューか、書き込みと同じトランザクションで更新するテーブルを使う。

**推奨**

- 読み込み用のデータストアを分ける完全な CQRS は、次の三つがそろうときに検討する。読み込みの負荷が書き込みより桁違いに大きいこと、通常の SQL では応答時間の要件を満たせないと測定で分かったこと、読み込み側の遅延(結果整合性)を利用者が許容できること。イベントソーシングは CQRS の前提ではなく、別の判断として扱う。

### feature 間の呼び出し

**必須**

- 他の feature のデータは、その feature の `index.ts` が公開する query で読む。他の feature の command は呼ばず、複数の feature の状態を変える操作は `app/` のルートで command を順に呼ぶ。他の feature のテーブルに直接触れない。
- 既定は同期の関数呼び出しとする。

**推奨**

- 呼び出し元が結果を待つ必要のない副作用(注文確定後の通知、監査ログ)は、プロセス内のイベントで分けてよい。イベントの中身はスキーマ付きのプレーンなデータにし、購読側の処理は発行側のトランザクションのコミット後に実行する。
  - 理由: コミット前に通知を送ると、ロールバックされた注文の通知が届く。
- イベントの取りこぼしが許されないときは、イベントを同じトランザクションでテーブルに書き、別の処理が配信する(トランザクショナルアウトボックス)。
